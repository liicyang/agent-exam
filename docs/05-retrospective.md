# 项目复盘

## 一、最难问题：让模型决策与实际执行结果保持一致

从这次项目的实现和验证结果来看，我认为最难的问题是：既让模型根据工具结果选择下一步，又保证它不会越过用户授权或错误报告执行结果。素材审核和排期涉及明确的业务约束，模型提出一个合理建议，并不意味着这个建议已经获得授权或已经执行成功。

例如，用户要求 18:00，但查询发现该时段已被占用。即使 19:00 可用，也只能先提出建议并等待确认。项目通过区分 `needs_confirmation`、`saved` 和 `failed` 等状态，并在保存工具中重新校验审核结果、时段占用和用户确认，保证状态与实际操作对应。最终是否保存成功依据工具返回值汇总，不依赖模型口头声称成功。

真实调用还暴露了一个具体问题：模型给零参数的 `read_material` 工具额外传入 `material_id`，导致调用被拒绝。离线 Mock 没有出现这个错误，说明模型对接口的理解需要单独验证。在 Codex 辅助下，项目强化了提示词中的参数说明，并让工具错误返回 `expected_arguments`，同时补充回归测试。修正后，八类真实验收场景全部通过。具体实现与调试分工见 [AI 使用记录](04-ai-usage.md)。

这一过程保留了 [首次失败记录](../examples/real/initial-argument-failure.json) 和 [修正后的验收结果](../examples/real/report.json)，可以对照检查问题、修改和验证依据。

## 二、学习收获

**第一，Agent 的动态决策需要用执行过程证明。** 仅有多个工具调用还不足以说明模型能根据环境调整行为。本项目中，正常场景继续保存，时段冲突场景转为请求确认；当额外占用 19:00 后，模型又把建议调整为 20:00。这些不同路径比单独展示最终答案更能说明模型如何使用工具结果。

**第二，模型的灵活性需要明确的工程边界。** 提示词负责说明任务和工具用法，程序仍要校验参数、限制可执行动作并保护保存操作。对于改期授权、重复提交和存储结果等要求，需要由业务代码和数据库约束保证。特别是幂等处理，需要同时考虑请求标识、内容是否变化以及数据库事务，不能只依靠模型判断“是否重复”。

**第三，离线测试与真实模型验证承担不同职责。** Mock 适合快速验证业务分支和异常处理，真实调用才能暴露模型传错参数、提前结束等问题。当前八类真实验收和十九项自动化测试提供了不同层面的证据，但固定用例的一轮通过不能直接代表所有输入下都稳定可靠。

**第四，交付材料应当让结果可以核对。** 在整理提交材料时，我要求明确每组输入、实际输出和 Trace 的位置，并补充代码架构说明。由此形成的交付思路是：需求对应验收场景，场景对应运行记录，评估结论引用具体文件。这样评审可以从结果追溯到工具调用，而不必只依赖文字描述。相关材料见 [评估文档](03-evaluation.md)。

## 三、下一步

我计划优先补充可靠性验证，再扩展业务功能：

1. **增加多轮真实模型评估。** 对相同场景重复运行，并增加输入改写、非法参数、接口超时等情况，记录任务完成率、工具调用次数和错误类型。重点确认当前通过的场景是否稳定，以及错误发生后能否明确结束。
2. **补充并发与幂等验证。** 增加多个请求同时抢占同一时段、同一请求重复到达等测试，检查数据库是否仍能保持单份草稿和唯一占用。当前已有顺序执行验证，尚未完成多进程并发压测。
3. **完善用户确认流程。** 增加明确的确认入口和确认记录，把当前输入字段中的授权扩展为可追踪的用户操作，并逐步支持草稿取消和重新排期。
4. **扩展排期与素材能力。** 在核心约束验证充分后，再考虑多素材批量处理、持续时间区间冲突及更丰富的审核规则。当前使用合成元数据，不将其视为真实视频内容审核能力。

目前已完成命令行核心流程、真实模型接入、草稿保存、八类验收和十九项自动化测试。上述多轮稳定性评估、并发压测及交互功能属于后续计划，尚未实现。实际总用时尚未记录，提交前需根据个人作答记录补充。
